# core.md — Project Core Rules

## Project Shape

- `examples/main/main.mygo` is the canonical design sample for the language surface.
- `internal/mygo/parser2/` owns syntax parsing with the parser-combinator library under `lib/text/parsec`.
- `internal/mygo/ast2/` owns the compact AST shared by the compiler pipeline.
- `internal/mygo/typeinference2/` owns Hindley-Milner inference and typeclass constraint solving.
- `internal/mygo/codegen2/` is the default AST-to-Go backend.
- `internal/mygo/codegen3/` is the opt-in IR-to-Go backend; `internal/mygo/ir3` and `internal/mygo/optimizer3` support it.
- `internal/mygo/compiler/` owns orchestration, the CLI-facing Go entry points, the codegen3 cache, and Go FFI bridges.
- `lsp/` is the self-hosted language server.
- `prelude/prelude.mygo` is the built-in prelude source that is merged into every package before lowering.
- Default bootstrap writes `zz_<source>.gen.go` next to each `.mygo` source; codegen3 writes into the configured cache. Generated Go is disposable and should be refreshed by the compiler.

## Compiler Pipeline

The default pipeline is:

```text
parser2 -> ast2 -> typeinference2 -> codegen2 -> .gen.go
```

An explicit `--codegen3` build uses the same front end followed by:

```text
parser2 -> ast2 -> typeinference2 -> ir3 -> optimizer3 -> codegen3 -> cache overlay
```

The backends have separate generated-Go ABIs. Codegen2 emits the legacy interface-based ADT representation; codegen3 emits canonical tagged representations. A package is never generated by both backends.

Use `go run ./cmd/mygo sync <dir>` to generate default output and `go run ./cmd/mygo build <dir>` to build after generation. See `docs/compiler2/core.md` for pipeline details and verification commands.

## Type Model

- Keep type parameters explicit in the AST and preserve them in generated Go.
- The current design follows Lisette-style nominal concrete types and structural interfaces.
- Generic enums, structs, interfaces, and functions should remain generic in emitted Go rather than collapsing to `any`.
- Prefer top-level generic functions over generic methods whenever the same behavior can be expressed that way. Use receiver methods only when Go requires them for type identity or interface conformance.
- Supported numeric types: `Int`, `Int8`, `Int16`, `Int32`, `Int64`, `UInt`, `UInt8`, `UInt16`, `UInt32`, `UInt64`, `Float32`, `Float64`. All map directly to Go primitives.
- Integer literals support hex (`0xff`), octal (`0o777`), and binary (`0b1010`) prefixes, producing number tokens with the raw literal string as value.
- Named primitive spellings like `Int`, `String`, and `Bool` map to Go primitives in generation.
- `()` (empty tuple) is the unit type in MyGO source and lowers to a Go function with no return values, not to `struct{}`. The old `Unit` spelling is no longer recognized.

## Workflow Notes

- Prefer small, focused changes that keep the example file in sync with compiler behavior.
- Keep `examples/main/main.mygo` runnable after compiler changes; its `main` function should actually do work, not only return a value.
- When checking the build, use a writable Go cache if the default cache path is unavailable in this environment.
- The prelude should be authored in MyGO when possible; if a prelude fragment cannot yet be expressed in MyGO, it may be implemented in Go as the lowest-level fallback.
