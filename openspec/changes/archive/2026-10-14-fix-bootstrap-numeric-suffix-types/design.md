## Context

动机见 proposal.md。`typeinference2.numberLiteralType` 已识别后缀并将类型写入表达式；`translateExprAstExpectedInner` 的数值分支只调用 `normalizeNumberLiteral` 剥除后缀，再构造无类型 Go 字面量。局部绑定虽记录推断类型，未注解时仍生成 `:=`；包级绑定则显式声明推断类型。

需要在编码前明确修复层级：只调整局部声明可以修复示例，却不能保证泛型或 `any` 实参中的数值类型。因此本设计选择表达式层面的类型保持。

## Goals / Non-Goals

**Goals:**
- 让数值表达式自身携带显式后缀的类型，避免依赖父节点恰好提供 Go 类型上下文。
- 将修复集中在数值字面量生成入口，复用 AST 类型与现有 Go 类型映射。
- 使用 Go 类型检查和运行时类型观察作为验收证据。

**Non-Goals:**
- 不统一重写所有局部绑定的声明策略。
- 不新增后缀、数值隐式转换规则或溢出诊断体系，不改 legacy 管线。
- 不调整无后缀数值的默认类型和语法接受范围。

## Decisions

### 1. 在数值表达式生成处输出类型转换

对带有已支持显式后缀的数值，输出与其推断类型一致的 Go 类型转换，例如 `int64(0)`、`float32(3.14)`。无后缀数值继续生成原来的常量表达式。这样局部声明可以继续使用 `:=`，同时调用参数和复合表达式也获得正确类型。

复用已推断的表达式类型以及既有 Go 类型映射；后缀识别和剥除集中处理，避免新建一份独立的后缀到类型映射。识别应沿用解析器支持的拼写范围；进制前缀和下划线保留为合法 Go 字面量，不经过浮点或宿主整数解析来重编码。

备选方案：仅使用推断类型生成 `var count int64 = 0`。该方案无法覆盖直接传入泛型或 `any` 的字面量，并扩大了局部绑定生成的改动范围，因此不采用。

### 2. 保持常量值和一元运算兼容

转换包裹数值常量，保留现有负号表达式路径。验证有符号最小值，避免把合法的 `-128i8` 错误生成成会先溢出的 `-int8(128)`；若 AST 将负号与数字分开，应将常量负号纳入转换操作数，再生成 `int8(-128)`。实现前用解析器实际 AST 确认该路径。

验证各整数类型边界、`UInt64` 大值、`Float32` 类型与舍入行为；超范围输入维持现有拒绝策略，不借类型保持引入截断语义。

### 3. 验证真实生成结果并同步自举产物

回归测试从 MyGO 源经过解析、推断和 codegen2，使用 Go 类型检查确认局部绑定及泛型结果类型，并通过调用或动态类型观察验证可执行结果。测试覆盖全部后缀、局部 `let/var`、负数、同类型算术、进制前缀、下划线及兼容上下文，避免仅断言输出字符串。

修改手写 `.mygo` 后通过现有自举流程刷新对应生成 Go；新增辅助逻辑放入小文件，遵守手写文件大小约束，不继续扩张已有大文件。无需调整推断规则，除非实施时发现与已确认行为不一致的证据。

## Risks / Trade-offs

- [负数最小值先转换正数导致溢出] → 对 AST 的一元负号路径增加边界回归，确保转换完整常量值。
- [显式类型影响泛型选择和动态类型观察] → 这是预期修复，测试同时验证 MyGO 推断与真实 Go 类型一致。
- [类型转换改变常量算术的检查位置] → 用同后缀算术及边界用例验证合法程序；不承诺扩展原有合法数值范围。
- [字面量被误当作后缀或丢失表示精度] → 沿用解析器接受范围，保留原始数字文本，不将数字解析后重新格式化。

## Migration Plan

实现并验证 codegen2 修复，使用当前自举工具刷新生成文件，再用更新后的编译器验证后缀探针。运行定向回归、自举检查及标准示例构建；使用可写的任务级 Go 缓存。无需数据迁移；回滚时同时恢复手写源和对应生成文件。
