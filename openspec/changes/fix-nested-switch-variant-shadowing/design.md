## Context

Reproduction (downstream `tutorial-video-generation`):

```mygo
switch read
  case Err(e) => return Err(e)
  case Ok(Some(x)) => return Ok(Step { Done: true, Execution: Some(x) })
  case Ok(None) => return Ok(Step { Done: false, Execution: None })
end
```

Generated Go:

```go
if m4, ok := read.(Result__Ok[Option[Execution], string]); ok { // Ok(Some(x))
    if m5, ok := m4.F0.(Option__Some[Execution]); ok {
        ...
    } else {
        if m3, ok := read.(Result__Ok[Option[Execution], string]); ok { // Ok(None)
            return ... // m3 never read
        }
    }
}
```

Instrumenting codegen's `valueName` decision shows the `Ok(None)` branch
asking for a real name even though its body reads nothing. That request
originates from the pattern shape, not from the emitted Go: the branch's
argument list is `[BindPattern("None")]`, not
`[VariantPattern("None", [])]`.

## Root cause

`internal/mygo/parser2/syntax_parse_types_patterns.mygo`
(`parsePatternIdentifier`) emits `BindPattern` for any bare identifier with
no following payload group — intentionally, since a context-free parser cannot
distinguish `x` the binding from `None` the constructor.

`internal/mygo/parser2/syntax_lower_types_patterns.mygo` lowers such a node to
`Pattern.BindPattern(text)`, so `Ok(None)` becomes
`VariantPattern("Ok", [BindPattern("None")])`.

Type inference already owns the disambiguation:
`resolveBareVariantPattern(env, state, targetType, pattern)` looks up the name
against the target enum declaration via `variantConstructorTypeForTarget` and
rewrites it to `VariantPattern(name, [])` when it is a non-function-shaped
variant. It handles the top-level `case None` case correctly, but it does not
recurse: its only branch is `case BindPattern(name)`, and every other pattern
falls through unchanged. Nested arguments therefore keep their unresolved
`BindPattern`.

## Goals / Non-Goals

**Goals:**

- Resolve bare identifiers at every nested pattern position against the type
  that owns that position.
- Fix the defect entirely inside type inference; codegen lowering is unchanged.

**Non-Goals:**

- Changing parser2's context-free bare-identifier rule.
- Changing codegen's `valueName` / elision heuristics (they are correct given a
  correct pattern tree).
- Changing case ordering or exhaustiveness behavior.

## Decisions

### D1: parser2 keeps bare identifiers as `BindPattern`

Adding type information to parser2 would either require threading the switch
target type into the parser or guessing. The existing split — parse
context-free, disambiguate with types — already works for the top-level case;
the defect is only that the disambiguation is not recursive.

### D2: recurse in `resolveBareVariantPattern`

Make the resolver walk the pattern tree. For `VariantPattern(name, args)` it
needs the field types of `name` in the current target type, applies the enum
parameter substitution, and resolves each argument against the corresponding
field type. For `TuplePattern(items)` it resolves each item against the
corresponding tuple element type.

The helper that yields variant field types already exists for the constructor
lookup: `variantConstructorTypeForTarget` returns `TFunc(fields, Ref)` for a
variant with payload, so the recursion reuses it. If it yields a non-`TFunc`
type the variant is zero-field and there is nothing to recurse into.

### D3: `StructVariantPattern` is left alone

Struct-variant fields are matched by name against a struct shape, so a bare
identifier there is a binding or a field shorthand, never a nullary enum
constructor. Recursing into it would be speculative.

### D4: no codegen change

Once inference produces `VariantPattern("None", [])`, codegen's existing
`patternArgsNeedValueName` sees a zero-argument pattern, and the `Ok(None)`
branch emits `if _, ok := read.(Result__Ok[...]); ok` — exactly the shape the
top-level `case None` case already produces.

## Risks / Trade-offs

- [Inference depends on the switch target type already being known] — this is
  the same precondition the existing top-level resolution has, so nested
  resolution inherits it rather than adding a new one. Include a case where the
  scrutinee type comes from a generic parameter to confirm no regression.
- [Bootstrap ordering] — `typeinference2` must be synced with the current
  `./mygo` before `codegen2` is synced with the rebuilt compiler; otherwise
  codegen2 would be regenerated by a compiler that cannot yet fix the pattern.
- [Type inference change is broad] — `typeinference2` is a large corpus of
  pattern matching; the acceptance gate is a clean sync of the whole
  self-hosted package set plus the downstream `tutorial-video-generation`
  build.
